# 客户与工单管理 SaaS：设计规格

日期：2026-10-30
状态：规格已批准并完成本地演示实现；当前验证结果与限制以 docs/project-status.md 为准。

## 1. 目标与验收范围

这是一个 React 前端面试作品，面向小型企业客服人员，展示客户维护和工单处理，以及 Claude Code / Codex 在明确规则、接口契约和可重复反馈下进行开发的能力。按 2–3 个工作日的投入组织，不以时间替代质量验收。

最终交付包含可本地运行的项目、两个关联模块的完整 CRUD、实际复用的公共组件、HTTP Mock、自动检查与 CI 配置，以及一次真实增量迭代的脱敏记录。演示应在 5–8 分钟内讲清业务闭环、复用、接口替换和验证过程。

默认中文界面、单个演示组织、固定操作员。不实现真实登录、权限、多租户隔离、计费、附件、导入导出、仪表盘、审计历史或回收站。不要求在线部署，不将演示入口描述为真实鉴权。

## 2. 业务模型与页面

### 2.1 客户

字段：服务端生成的 id、name、contactName、email、可选 notes、createdAt、updatedAt。

- name 去除首尾空格后为 1–100 字，contactName 为 1–50 字；email 必填并校验格式；notes 最多 1,000 字。
- 允许客户名称和邮箱重复，以 id 区分记录。
- 列表按名称或邮箱搜索，支持分页；详情展示完整信息及查看关联工单入口。
- 新增和编辑复用客户表单；删除前二次确认。
- 存在任何关联工单的客户均禁止删除，包括工单已完成的情况；服务端/Mock 在删除操作时执行约束并返回 409。
- 客户改名后，关联工单展示最新名称，不能把名称副本作为事实来源。

### 2.2 工单

字段：服务端生成的 id、title、customerId、description、priority、status、createdAt、updatedAt。

- title 去除首尾空格后为 1–100 字；description 为 1–2,000 字；customerId 必须引用存在的客户。
- priority 为 low / medium / high，界面显示低 / 中 / 高，默认 medium。
- status 为 pending / in_progress / completed，界面显示待处理 / 处理中 / 已完成；新建固定为 pending。
- 合法变更为 pending → in_progress → completed，以及 completed → in_progress；保留原状态的普通编辑允许提交，其余流转返回 409。
- 列表按标题搜索，按客户、状态、优先级组合筛选，支持分页；详情显示全部字段。
- 新增、编辑时客户选择器支持搜索和分页，并能回显未在当前选项页中的已选客户；客户不存在时不可提交。
- 没有客户时提示先创建客户；所有状态的工单均允许经二次确认后删除。

### 2.3 统一交互与边界

- 默认每页 20 条，可选 10、20、50；搜索或筛选改变后回到第一页。
- 列表默认按 createdAt 降序、id 稳定排序；删除后页面为空且有前一页时，退回前一页重新查询。
- 区分首次加载、无数据、无搜索结果和请求失败；失败支持重试并保留筛选。
- 提交期间禁止重复操作；写请求不自动重试。失败保留表单输入并展示字段错误或全局错误。
- 有未保存修改时关闭表单需确认；成功保存后不再提示。切换编辑对象时重新初始化表单。
- 查询键包含分页和筛选参数；使用取消信号避免旧搜索结果覆盖当前结果。
- 编辑或删除时记录不存在返回 404：告知用户，关闭失效表单并刷新列表。
- 响应缺少必要字段或结构不合法时展示可定位错误，不能伪装成空数据；可选字段安全显示空值。
- 时间传输使用 ISO 8601，按浏览器本地时区显示 YYYY-MM-DD HH:mm:ss。
- 窄屏表格支持横向滚动，表单适应可用宽度；按钮有可访问名称，弹窗支持键盘、焦点管理和错误提示。
- 本版本采用后写覆盖，不提供多人版本冲突保护或跨标签页事务保证。

## 3. 技术架构与公共组件

选择 React SPA + MSW。相比独立 Mock 服务，该方案减少启动依赖；相比页面直接读写本地数据，该方案保留 HTTP 契约和异常处理边界。

技术栈：React、TypeScript、Vite、React Router、Ant Design 及其图标库、TanStack Query、原生 fetch 薄封装、OpenAPI 3.1、MSW、ESLint、Vitest、Testing Library、Playwright、GitHub Actions。实施时核实兼容版本，固定 Node 和 npm 版本，提交依赖锁文件；不引入第二套 UI、表单或全局状态库。

数据流：页面和公共组件 → 业务查询/变更 hooks → 类型化 API 客户端 → HTTP → MSW 或真实后端。

模块边界：

- features/customers、features/tickets：业务页面、字段、查询及业务规则；禁止互相导入内部实现，通过公共契约和路由协作。
- shared：公共组件、请求基础设施、展示工具；不依赖业务页面。
- contracts：OpenAPI 源文件与生成类型；生成文件不手工修改。
- mocks：处理器、数据仓库、种子和场景；业务代码禁止导入或直接读取 Mock 存储。
- tests：契约及跨模块验证。

公共组件：

| 组件 | 统一职责 | 业务保留的职责 |
| --- | --- | --- |
| DataTable | 分页、加载、空态、错误、重试 | 列定义、筛选、行操作 |
| FormDialog | 打开关闭、提交中、未保存确认 | 字段、校验、提交业务 |
| DeleteConfirm | 二次确认、进行中与失败反馈 | 删除对象、关联约束提示 |

两个模块必须实际复用这些组件。不建设 JSON 表单引擎；服务端状态交给 TanStack Query，表单和弹窗状态保留在组件内部。

## 4. 接口与协作契约

OpenAPI 为接口事实来源，生成 TypeScript 类型，并通过运行时响应校验与契约测试验证边界；仅有编译通过不算契约验收。

customers 和 tickets 均提供：

| 方法 | 路径模式 | 行为 |
| --- | --- | --- |
| GET | /api/{resource} | 搜索、筛选与分页 |
| POST | /api/{resource} | 创建，返回 201 和资源 |
| GET | /api/{resource}/{id} | 详情，返回 200 和资源 |
| PATCH | /api/{resource}/{id} | 更新，返回 200 和资源 |
| DELETE | /api/{resource}/{id} | 删除，返回 204，无响应体 |

- 列表参数：q、page、pageSize；工单额外接受 customerId、status、priority。page 从 1 开始，pageSize 为 10、20、50，缺省分别为 1、20；非法参数返回 422。
- q 去除首尾空格后按不区分大小写的子串匹配，空字符串等价于不筛选；多个筛选条件取交集。
- 列表响应为 { items, total, page, pageSize }，详情和写入成功直接返回资源对象。
- 工单读取模型含基于关联客户生成的 customerName，仅供展示；写入只接受 customerId。
- 错误响应为 { code, message, fieldErrors? }，fieldErrors 为字段名到错误文本的映射。
- 422 表示请求校验失败，404 表示记录不存在，409 表示有关联记录或非法状态流转；网络及 5xx 错误按全局可重试错误展示。
- ID 和时间由服务端/Mock 生成；PATCH 只接受可编辑字段，缺省字段保持原值，可选 notes 以空字符串清空。
- 写入必须先完成校验再修改数据，失败不得留下部分更新。
- 成功写入后使相关列表、详情和关联查询失效；客户改名须刷新工单读取模型，删除工单须使客户关联视图更新。

后端协作流程：先改契约及示例 → 生成类型 → 更新 Mock 和契约测试 → 前端消费接口 → 执行验收。真实后端接入时关闭 Mock、配置 API 地址，并对后端验证同一契约；鉴权与 CORS 等接入配置需在实际联调阶段验证，不声称已验证。

## 5. Mock 与演示数据

- 固定种子包含多个客户、超过一页的工单及所有状态和优先级组合，数据均为虚构。
- 浏览器 Mock 通过带版本号的 localStorage 仓库存储，刷新保留数据；页面不能直接访问仓库。
- 明确提供演示控制入口，用户确认后重置种子；重置后清理查询缓存并重新获取数据。
- 存储损坏、版本不兼容或不可写时显示提示，不静默覆盖数据；可由用户确认重置，无法持久化时明确提示改用当前会话内存模式。
- 延迟、失败、空数据场景通过明确控制或测试处理器启用，不使用随机失败；演示控制不混入业务表单。
- Node 测试使用独立内存仓库，浏览器测试使用独立上下文；每个测试重建种子，禁止依赖其他测试的执行顺序。
- MSW 在首个业务请求发出前准备完毕；只拦截约定 API。缺少匹配处理器的 API 请求在测试中失败，在演示中明确提示，不意外发送到外部服务。
- dev 默认启用 Mock；演示构建显式启用 Mock。真实 API 模式禁用 Mock，并清理先前注册的本应用 Mock worker，避免模式切换残留。

## 6. Harness 工程交付

Harness 定义：使 AI 能定位项目、在明确边界内修改、获得可重复反馈，并由人审阅结果的工程环境。

| 交付 | 责任 |
| --- | --- |
| AGENTS.md | Agent 权限、禁止事项、模块导航、常用命令；遵循用户全局规则 |
| CLAUDE.md | 引导读取共同规则，避免维护两份矛盾流程 |
| RULES.md | 架构依赖方向、契约变更要求、完成标准 |
| README | 启动、环境、Mock 模式、重置、验收路径、已知限制 |
| 检查脚本 | lint、类型、测试、构建、E2E；失败返回非零退出码 |
| CI | 调用同一本地验证流程，必要时保存测试报告 |
| 迭代记录 | 真实需求、影响范围、检查命令及结果、人工复核和剩余风险 |

命令契约：npm run dev、lint、typecheck、test、test:e2e、build、verify。test 为非 watch 模式；verify 串行完成 lint、typecheck、test、build、test:e2e。README 给出 npm ci、浏览器测试依赖安装及运行说明。测试仅访问本地应用和隔离数据，不调用外部服务。

静态检查限制跨模块内部导入、shared 对 features 的反向依赖以及业务代码导入 mocks；契约检查验证生成类型与规范一致，防止契约变更后忘记生成。CI 使用固定运行环境和锁文件安装，执行与本地相同的验收脚本；配置存在不等于 CI 已运行成功。

真实增量迭代：基础 CRUD 完成后，单独增加工单优先级筛选。最终交付包含该功能，过程记录其需求、契约变化、Mock、页面、测试及实际反馈，不编造失败或成功记录。只记录脱敏元数据，不保存原始提示词、密钥、请求体或完整对话。

## 7. 验证与交付标准

| 层次 | 必须覆盖 |
| --- | --- |
| 规则 | 字段边界、合法与非法状态流转、关联删除限制 |
| 集成 | 失败保留输入、防重复提交、空态、重试、失效记录处理 |
| 契约 | 请求参数、响应结构、分页、422/404/409、生成类型一致 |
| 浏览器 | 两模块完整 CRUD；有关联客户不可删除；删除工单后可删除客户；搜索筛选分页；刷新持久化 |
| 回归 | 删除末条页码恢复、快速切换查询、客户改名同步、已选客户回显 |
| 人工 | 窄屏、键盘、焦点、提示可读性、控制台错误、5–8 分钟演示 |
| 交付 | 新环境可运行、构建通过、最终差异审查、密钥扫描、准确限制说明 |

依赖安装可能需要网络，但测试与应用演示不依赖在线第三方业务服务。若额外测试涉及费用、持久数据或外部服务，按用户规则单独处理授权。

## 8. 阶段与范围控制

1. 工程基础：规则、应用壳、契约、种子、Mock、检查命令；证明启动和一次请求正常。
2. 客户纵向闭环：完整 CRUD 及公共组件；证明 UI 到 Mock 的闭环。
3. 工单关联：完整 CRUD、客户关联、状态与删除规则；证明复用与跨模块约束。
4. 异常与增量迭代：优先级筛选、异常场景、回归及证据。
5. 交付整理：CI、README、演示路径、最终审查及未验证事项。

每个阶段以验收结果而非代码量完成。不默认为生产可用，不自动部署、提交或推送；Git 提交和推送遵循用户明确授权。项目文件如需移除须移入旧内容/，不得直接删除。不创建私人 Wiki。
